## Scope decisions (set by the user when this plan was generated)

- **Location**: the integration lives **inside this monorepo** under
  `integrations/home-assistant/` (CI + pytest co-located). HACS distribution to
  end users happens later via a dedicated mirror repo that exposes
  `custom_components/devicesdk/` at its root - that mirror is out of scope here.
- **Scope**: **full v1**, built in independently-verifiable phases (config flow,
  REST discovery, live watch-WebSocket state, connectivity sensor, read
  entities, and controllable switch/light entities), plus pytest tests.
  The `number` entity type is explicitly deferred (no server-side command to set
  a value exists yet - see plan 001 "Deferred / out of scope").

## Dependency notes

- 002 **depends on 003** (revised 2026-07-05): 002's original Phase 1
  published the npm stdio `@devicesdk/mcp` to the official MCP registry, and
  003 deletes that package from the repo (owner decision 2026-07-05: no users
  rely on it), replacing it with the server-bundled `/mcp` endpoint. 002's
  Phase 1 is REJECTED in place (the registry cannot list a self-hosted remote
  URL, so there is no replacement entry); its remaining phases (Claude Code
  plugin, README section, markdown-mirror links, JSON-LD) are additive-only
  and their agent-facing copy now describes the `/mcp` endpoint, so they must
  run after 003 lands. 002 remains independent of 001; its appendix lists
  human outreach tasks (directory submissions) that are NOT executor work.
  One appendix item (Home Assistant forum post) is best done after 001 ships,
  but nothing in 002 blocks on it.
- 001 is self-contained. It only **reads** the existing DeviceSDK server API
  (already shipped); it adds a new, isolated Python package and one CI workflow.
  It does not modify `apps/`, `packages/`, the pnpm workspace, or Turbo.
- 005 has a **soft** dependency on 004: it reuses the hex byte helpers 004
  creates in `packages/core/src/bytes.ts`. If 004 has not landed, 005's scope
  includes creating them itself (spec inlined in both plans).
- 006 is independent of 004/005 (different transports) but is the only plan
  touching firmware; its firmware verification happens in CI, and hardware
  validation is an explicit owner step before the release PR merges.
- 004 pairs well with 001: every driver's readings can be exposed to Home
  Assistant via the existing `emitState` + entity declarations.
